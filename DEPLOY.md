# Правовой консультант — публикация и автообновление

Приложение — статический сайт без сервера и без сборки: HTML, CSS, один
`app.js` и данные в `data/`. Работает и с `file://`, и с любого хостинга.
Ниже — как выложить его так, чтобы он **обновлялся сам у всех посетителей**,
и как просто загружать новые файлы, когда что-то изменилось.

---

## Короткий путь: от нуля до живого сайта

Если вы ещё ничего никуда не загружали — вот вся последовательность целиком.
Подробности по каждому шагу — в разделах ниже.

**Шаг 1. Настроить git (один раз на компьютере).**
Без имени и почты git откажется делать коммит:

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "ваша@почта"
```

> **Если PowerShell пишет «Имя "git" не распознано».** Значит, отдельного Git на
> компьютере нет — есть только переносимый, который поставляется вместе с
> приложением. Он лежит в
> `C:\Program Files\WorkBuddyAI\resources\vendor\PortableGit\`. Добавьте его в
> `Path` текущего окна PowerShell — и команды заработают:
>
> ```powershell
> $env:Path += ";C:\Program Files\WorkBuddyAI\resources\vendor\PortableGit\cmd"
> ```
>
> Настройка действует до закрытия окна: откроете новое — повторите строку.
> Чтобы `git` работал всегда и во всех программах, поставьте обычный
> [Git for Windows](https://git-scm.com/download/win) — установка со всеми
> настройками по умолчанию.

**Шаг 2. Создать пустой репозиторий на GitHub.**
[github.com](https://github.com) → **New repository** → имя, например
`pravovoy-konsultant` → **Private** → не добавлять ни README, ни `.gitignore`
(иначе первый push конфликтует) → **Create repository**.

**Шаг 3. Отправить проект в репозиторий.** Из папки проекта:

```bash
git init                       # если папка ещё не репозиторий; повторный запуск безвреден
git add .
git commit -m "Правовой консультант: первая публикация"
git branch -M main
git remote add origin https://github.com/<ваш-логин>/pravovoy-konsultant.git
git push -u origin main
```

Уйдёт **304 файла, ~102 МБ** — на небыстром канале это несколько минут.

**Шаг 4. Разрешить ночной сборке писать в репозиторий.**
Репозиторий → **Settings → Actions → General → Workflow permissions** →
**Read and write permissions** → **Save**.

**Шаг 5. Подключить хостинг.**
[dash.cloudflare.com](https://dash.cloudflare.com) → **Workers & Pages →
Create → Pages → Connect to Git** → выбрать репозиторий, дать доступ →
**Project name:** `pravovoy-konsultant` (**это и есть адрес сайта**) →
**Build command:** `node tools/build-dist.js` →
**Build output directory:** `dist` → **Save and Deploy**.

**Шаг 6. Проверить.**
Открыть `https://pravovoy-konsultant.pages.dev` — сайт должен работать.
Затем `https://pravovoy-konsultant.pages.dev/data/version.json` — должен
вернуться JSON с отпечатком сборки.

Готово. Дальше сайт обновляется сам: ночью GitHub Actions проверяет законы и,
если что-то изменилось, коммитит; хостинг перевыкладывает; открытые вкладки
предлагают обновиться.

### Что делать потом

| Задача | Что сделать |
|----|----|
| Поправить текст или оформление | `git add . && git commit -m "Правка" && git push` |
| Обновить базу прямо сейчас, не ждать ночи | Actions → «Обновление базы» → **Run workflow** |
| Посмотреть, что изменилось за ночь | вкладка **Actions** → последний прогон → **update-logs** |
| Узнать версию базы у читателя | раздел **«Проверка актуальности»** в приложении |

> **Почему репозиторий приватный.** В него попадает ещё и память проекта
> (`.workbuddy-ai/memory/`) — рабочие заметки. Публичный репозиторий тоже
> подойдёт, но тогда эти заметки станут видны; для публичного лучше исключить
> `.workbuddy-ai/` целиком, оставив одну строку в `.gitignore`.

## 1. Что где живёт

| Что | Где | Зачем |
|----|----|----|
| Сайт | `index.html`, `app.js`, `styles.css`, `data/*.js` | то, что отдаётся посетителю |
| **Каталог публикации** | **`dist/`** | **ровно то, что уходит на хостинг — собирается `npm run dist`** |
| Данные (собраны) | `data/` — 227 источников, 19 307 статей, полные тексты, лента «Новое» | ~101 МБ |
| Сырые выгрузки | `vendor/` | **в git не входят** — каждый прогон качает заново |
| Инструменты | `tools/` | загрузка, сборка, аудит, проверки, лента |
| Ночная сборка | `.github/workflows/update.yml` | скачать → собрать → проверить → закоммитить |

**Размеры — это главное, что нужно знать до выбора хостинга.**

| Показатель | Значение |
|----|----|
| Каталог публикации `dist/` | **278 файлов, 100,3 МБ** |
| Самый большой файл | `data/full/nk2.js` — **9,6 МБ** |
| `data/` целиком | ~101 МБ |
| Из них полные тексты `data/full/` | 89,9 МБ (227 файлов) |

Ограничение GitHub — 100 МБ на отдельный файл, так что push пройдёт без
дополнительных настроек. А вот **у бесплатного Vercel лимит на общий размер
загружаемых файлов — 100 МБ**, и проект в него не укладывается (см. раздел 3).

## 2. Автообновление у посетителей (как это устроено)

Требование было: «чтобы сайт у всех сам автоматически обновлялся». Работают
две независимые части — ночная пересборка на GitHub и опрос версии в браузере.

### 2.1. Отпечаток сборки

`tools/build-data.js` вместе с данными пишет крошечный `data/version.json`:

```json
{"at":"2026-10-12T01:45:35.064Z","digest":"e7dfe6191e8bc64a","articles":19307,"sources":227,"files":271}
```

`digest` — это sha1 по содержимому всех `data/*.js` и `data/*.json`, у которых
предварительно обнулена метка времени `built_at`. Поэтому отпечаток меняется
**только вместе с самими данными**, а не каждую ночь: иначе все открытые вкладки
перезагружались бы впустую. Проверено: два прогона подряд дают одинаковый
`digest` при разном `at`.

### 2.2. Что делает браузер

`app.js` при старте один раз тихо читает `data/version.json` (с `cache:
"no-store"`), запоминает отпечаток в `localStorage` под ключом
`rflaws.buildDigest` и дальше перепроверяет его:

- раз в **45 минут**;
- при **возврате во вкладку** (`visibilitychange`), но не чаще раза в 5 минут.

Если отпечаток на хостинге разошёлся с загруженным — снизу появляется
уведомление **«Вышла новая редакция базы»** с числом статей и кнопками
«Обновить» и «Скрыть» (скрытие действует до конца сеанса). Кнопка «Обновить»
перезагружает страницу по адресу с меткой версии (`?v=<отпечаток>`), поэтому и
документ, и данные приходят из сети, а не из кеша.

Тяжёлые ленивые файлы (`data/ft/*`, `data/full/*`) тоже запрашиваются с
`?v=<отпечаток>`, иначе после выкладки браузер отдал бы из кеша старые тексты.

**Важная деталь.** Свежая загрузка страницы всегда отдаёт текущую сборку —
поэтому уведомление не показывается тем, кто просто открыл сайт (при старте
отпечаток молча запоминается). Оно адресовано тем, **кто читает приложение в
момент выкладки новой версии**: для них перезагрузка — единственный способ
получить новые тексты. Текущую версию всегда видно в разделе
**«Проверка актуальности»** — строка «Версия базы в этой вкладке».

### 2.3. Ночная пересборка

Хостинг сам по себе не умеет скачивать законы с pravo.gov.ru — поэтому
расписание живёт в GitHub Actions (для публичных репозиториев он бесплатен и
без лимитов). См. раздел 4.

## 3. Куда публиковать

### 3.0. Что именно уходит на хостинг

В корне репозитория лежит не только сайт: там же `tools/` (исходники сборщика),
`.github/` (ночная сборка), `package.json` и эта инструкция. Отдавать корень
целиком не стоит — служебные файлы стали бы доступны по прямым ссылкам. Поэтому
публикуется собранный каталог `dist/`:

```bash
npm run dist      # собирает dist/ из index.html, app.js, styles.css, favicon.svg и data/
```

Скрипт `tools/build-dist.js` кладёт туда же:

- **`_headers`** — правила кеширования. Они не дублируются, а **выводятся из
  `vercel.json`**: два списка рано или поздно разошлись бы, и кеш на Vercel
  отличался бы от кеша на Cloudflare;
- **`.nojekyll`** — без него GitHub Pages выбрасывает файлы, начинающиеся с
  подчёркивания, то есть сам `_headers`.

`dist/` в git не хранится — это производная от `data/`, её собирает хостинг.

Посмотреть, что именно уедет на хостинг, можно локально:

```bash
node tools/serve.js 8123 dist     # http://localhost:8123 — ровно содержимое dist/
```

Сборщик сам сообщает объём и предупреждает, если превышены пределы бесплатного
Cloudflare Pages (25 МБ на файл, 20 000 файлов).

### 3.1. Сравнение

| Хостинг | Лимит | Наш `dist/` (100,3 МБ, 278 файлов, макс. 9,6 МБ) |
|----|----|----|
| **Cloudflare Pages**, бесплатно | 25 МБ на файл, 20 000 файлов, трафик без лимита, 500 сборок в месяц | ✅ с запасом |
| **GitHub Pages**, бесплатно | 1 ГБ на сайт, 100 ГБ трафика в месяц, 10 сборок в час | ✅ подходит |
| **Vercel Hobby**, бесплатно | **100 МБ на загрузку деплоя** | ❌ не укладывается |
| **Vercel Pro** | 1 ГБ на загрузку | ✅ подходит |

Netlify в список не попал намеренно: у него бесплатный план — **300 кредитов в
месяц**, а трафик стоит 20 кредитов за гигабайт, то есть около **15 ГБ в месяц**.
Справочник с полными текстами актов израсходует это за пару тысяч посещений.

### 3.2. Рекомендация

**Берите Cloudflare Pages** (§3.4). Дело не только в лимитах: там **трафик не
тарифицируется**, а справочник по законам читают много и подолгу — на GitHub
Pages мягкий предел 100 ГБ в месяц рано или поздно станет тесен. Плюс можно
задать свои заголовки кеширования, а именно на них держится мгновенное
обновление из раздела 2.

Адрес сайта получается из **названия проекта**, которое вы вписываете сами при
создании (`pravovoy-konsultant.pages.dev`) — ни почты, ни логина в нём нет.

**GitHub Pages** (§3.5) — если не хочется подключать ещё один сервис:
репозиторий на GitHub нужен в любом случае, там живёт ночная сборка. Минус один:
свои заголовки задать нельзя, кеш там фиксированный (10 минут), поэтому новая
версия доходит до читателя не мгновенно, а в пределах десяти минут.

**Vercel** (§3.6) — только платный Pro. Бесплатный Hobby принимает не более
**100 МБ** исходных файлов на деплой, а у нас 100,3 МБ одних данных; деплой
упадёт с ошибкой о размере.

> **Можно ли всё-таки остаться на бесплатном Vercel?** Да, но ценой лишней
> зависимости: 90 из 100 МБ — это `data/full/` (полные тексты актов), и их
> можно вынести за пределы деплоя, отдавая с внешнего адреса. Тогда деплой
> сжимается до ~10 МБ и проходит где угодно. Плата — доступность справочника
> начинает зависеть от чужого сервиса, который вы не контролируете. Ради
> экономии 20 $ в месяц это обычно не стоит того.

### 3.3. Первый push на GitHub (нужен для любого варианта)

```bash
git init
git add .
git commit -m "Правовой консультант: первая публикация"
git branch -M main
git remote add origin https://github.com/<ваш-логин>/<репозиторий>.git
git push -u origin main
```

`.gitignore` исключает `vendor/`, `node_modules/`, `dist/` и рабочие файлы
ассистента (профили браузера, резервные копии, снимки экрана), поэтому в
репозиторий уйдёт только сайт с собранными данными.

Репозиторий может быть и приватным — для GitHub Actions этого достаточно.
Публичным его делать нужно только в одном случае: если вы решите отдавать
данные с `raw.githubusercontent.com` (тот самый обход лимита Vercel выше).

### 3.4. Cloudflare Pages (бесплатно, рекомендуется)

1. [dash.cloudflare.com](https://dash.cloudflare.com) → **Workers & Pages →
   Create → Pages → Connect to Git**, выберите репозиторий из §3.3.
2. **Project name** — впишите название сайта, например `pravovoy-konsultant`.
   **Именно из этого поля получится адрес**, и его вы выбираете сами; почта
   аккаунта в адрес не попадает (подробнее ниже).
3. Настройки сборки:
   - **Build command:** `node tools/build-dist.js`
   - **Build output directory:** `dist`
   - **Root directory:** оставьте пустым (корень репозитория)
4. **Save and Deploy.** Через минуту-две сайт будет доступен на
   `https://pravovoy-konsultant.pages.dev`.
5. Дальше каждый `git push` в `main` — в том числе коммит ночной сборки —
   перевыкладывает сайт автоматически. Ничего настраивать больше не нужно.

Если выбранное имя уже занято другим проектом Cloudflare, к нему добавятся
несколько случайных символов (`pravovoy-konsultant-a1b2.pages.dev`) — просто
возьмите другое слово. Уже созданный проект можно переименовать: **Settings →
Project name**; адрес изменится вместе с именем.

Свой домен: **Custom domains → Set up a domain**. Подключается бесплатно,
сертификат выпускается сам.

**Про адрес сайта.** `https://<название-проекта>.pages.dev` — это название
**проекта**, а не аккаунта, и почта в него не попадает. По умолчанию Cloudflare
подставляет имя git-репозитория, но его можно заменить на любое: при создании —
в поле **Project name**, позже — в **Settings → Project name**. Например, имя
`pravovoy-konsultant` даёт адрес `pravovoy-konsultant.pages.dev`.

Если подсказка в поле имени выглядит как адрес вашей почты (`ivan-gmail-com`) —
это лишь значение по умолчанию для аккаунтов, заведённых через почту. Сотрите
его и впишите любое слово. А если не хочется и `pages.dev`, подключите свой
домен — тогда адрес будет полностью вашим.

**Проверка после первого деплоя.** Откройте
`https://<проект>.pages.dev/data/version.json` — должен вернуться JSON с
отпечатком (`{"at":…,"digest":…}`). Если вместо него пришёл HTML, значит
каталог сборки указан неверно и отдаётся что-то другое.

### 3.5. GitHub Pages (бесплатно, без сторонних сервисов)

1. В репозитории: **Settings → Pages → Build and deployment → Source:
   GitHub Actions**.
2. Создайте `.github/workflows/pages.yml`:

   ```yaml
   name: Публикация
   on:
     push: { branches: [main] }
     workflow_dispatch:
   permissions:
     pages: write
     id-token: write
     contents: read
   concurrency:
     group: pages
     cancel-in-progress: false
   jobs:
     deploy:
       runs-on: ubuntu-latest
       environment:
         name: github-pages
         url: ${{ steps.deployment.outputs.page_url }}
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-node@v4
           with: { node-version: 22 }
         - run: node tools/build-dist.js
         - uses: actions/configure-pages@v5
         - uses: actions/upload-pages-artifact@v3
           with:
             path: dist
         - id: deployment
           uses: actions/deploy-pages@v4
   ```

3. Дальше сайт сам выкладывается на каждый `push` в `main` — включая коммиты
   ночной сборки.

Сайт будет доступен по адресу `https://<логин>.github.io/<репозиторий>/`.
Приложение использует относительные пути, поэтому в подкаталоге работает
без правок.

### 3.6. Vercel (платный план)

1. [vercel.com](https://vercel.com): **Add New → Project → Import Git
   Repository**, выберите репозиторий из §3.3.
2. **Build command:** `node tools/build-dist.js`, **Output directory:** `dist`.
3. **Deploy.** Адрес вида `https://<проект>.vercel.app`.

> **Почему на бесплатном плане не получится.** Vercel Hobby принимает не более
> **100 МБ** исходных файлов на деплой, а у нас 100,3 МБ одних данных. Деплой
> упадёт с ошибкой о размере. Варианты: Pro (лимит 1 ГБ) либо Cloudflare
> Pages / GitHub Pages.

### Что уже настроено для кеша

Правила заданы в `vercel.json` и переносятся в `dist/_headers` при сборке:

- `/`, `/index.html`, `/app.js`, `/styles.css` — `max-age=0, must-revalidate`:
  при каждом заходе браузер перепроверяет файл, поэтому новая версия сайта
  видна сразу после деплоя;
- `data/*.js` верхнего уровня (`index.js`, `registry.js`, `version.json`…) —
  тоже всегда перепроверяются;
- `data/full/*` и `data/ft/*` (тяжёлые полные тексты) — 10 минут кеша с
  фоновым обновлением. После выкладки браузер подхватывает их по метке
  `?v=<отпечаток>`, поэтому залипнуть надолго они не могут.

На GitHub Pages свои заголовки задать нельзя — там кеш управляется правилами
самого GitHub. Механизм из раздела 2 всё равно работает: метка версии в адресе
перезагрузки обходит кеш и там.

## 4. Автообновление базы: GitHub Actions

Файл `.github/workflows/update.yml` запускается **каждый день в 23:30 МСК** и
делает по шагам:

1. `fetch-sources.js` — кодексы и федеральные законы из открытого набора
   `ruslaw-public` (первоисточник — actual.pravo.gov.ru);
2. `fetch-extra.js` — Конституция, ФКЗ и метаданные прямо с портала;
3. `fetch-plenums.js` — постановления Пленума ВС РФ (sudact.ru);
4. `build-data.js` — пересборка `data/` (реестр, индекс, статусы, полнотекст)
   **и запись нового `data/version.json`**;
5. `build-changelog.js` — сравнение с предыдущим снимком и лента изменений
   для вкладки «Новое»;
6. `audit.js` → `verify-data.js` → `smoke-test.js` — три проверки;
7. если хоть что-то изменилось и все проверки зелёные — коммит и `push`.
   Хостинг видит push и перевыкладывает сайт, а открытые вкладки замечают
   новый отпечаток и предлагают обновиться.

**В `main` попадает только то, что прошло проверки.** Если хоть одна красная —
задача падает, коммита нет, на сайте остаётся прежняя база.

Сравнение «что изменилось» игнорирует сам `data/version.json`: его метка
времени меняется каждый прогон, а содержимое следует за остальными файлами.
Без этого правила коммит появлялся бы каждую ночь даже без изменений в законах.

### Включить

Ничего включать не нужно: файл в репозитории — задача появится в разделе
**Actions** сразу после первого пуша. Расписание начнёт работать в течение
часа (GitHub может задержать первый запуск).

**Запустить вручную:** Actions → «Обновление базы» → **Run workflow**.
Там же можно отметить «пересобрать даже без изменений».

**Логи любого прогона** (в том числе упавшего) — во вложении `update-logs`.

## 5. «Просто загрузить новые файлы»

Отдельного файлового менеджера не нужно — обновление это обычный коммит.

**Свой текст или правка интерфейса:**

```bash
git add .
git commit -m "Правка текста справки"
git push
```

Хостинг перевыложит сайт за минуту-две; открытые вкладки покажут уведомление
из раздела 2.

**Только данные о статьях:**

```bash
npm run build      # скачать свежие тексты с портала и пересобрать data/
npm run verify     # три проверки: audit + verify-data + smoke-test
git add data tools/state/snapshot.json
git commit -m "Обновление базы"
git push
```

Руками править `data/*.js` не нужно: это результат сборки. Собирать `dist/`
локально тоже не нужно — это делает хостинг при каждом деплое. Если очень
хочется залить без git, можно собрать `npm run dist` и загрузить каталог
`dist/` через веб-интерфейс хостинга (Cloudflare Pages → **Create new
deployment** → Direct Upload), но тогда автоматической ночной сборки не будет:
её выполняет только GitHub Actions.

## 6. Вкладка «Новое»

Заполняется автоматически ночной сборкой. Одна запись — один документ на одну
дату проверки:

- сменилась редакция (с указанием прежней и новой даты);
- добавились, изменились или исчезли статьи — со ссылками на каждую;
- нормы утратили силу или снова действуют — со ссылками на статьи;
- документ добавлен в базу или убран из неё.

У непросмотренных записей в боковом меню горит счётчик и точка; кнопка
**«Отметить прочитанным»** снимает их. Просмотр не требует сети — лента уже
лежит в собранной базе (`data/changelog.js`).

Если лента пуста, раздел так и говорит: «Лента пока пуста» — с инструкцией,
чем её запустить.

## 7. Локальные команды

```bash
npm run verify     # три проверки: audit + verify-data + smoke-test
npm run build      # полный цикл: скачать → собрать → лента
npm run build:data # только пересборка данных и ленты (без скачивания)
npm run changelog  # пересчитать ленту из текущих данных
npm run dist       # собрать каталог публикации dist/
npm run serve      # http://localhost:8080 — просмотр как на хостинге
node tools/serve.js 8123 dist   # просмотр ровно того, что уедет на хостинг
node tools/smoke-test.js        # прогон интерфейса (нужен jsdom: npm ci)
```

Первый `npm run build` скачает ~92 МБ сырых выгрузок в `vendor/` — в git они не
идут, так что при клонировании репозитория их нужно получить этой командой.

Проверить отпечаток сборки вручную:

```bash
cat data/version.json
```

---

## 8. Правило хранения ленты

Лента не растёт бесконечно: `tools/build-changelog.js` оставляет записи за
последние **180 дней**, но не больше **400 штук**. Сравниваемый снимок лежит в
`tools/state/snapshot.json` — он нужен сборке, но в браузер не попадает.

Если ночная сборка не смогла ничего изменить (портал недоступен, проверка
красная), коммита не будет — и лента останется честной, без придуманных записей.
