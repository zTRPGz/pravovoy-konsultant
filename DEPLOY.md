# Правовой консультант — публикация и автообновление

Приложение — статический сайт без сервера и без сборки: HTML, CSS, один
`app.js` и данные в `data/`. Работает и с `file://`, и с любого хостинга.

Сайт уже опубликован и обновляется сам. Этот файл — про то, как он
публикуется, что делать при правках и где смотреть, если что-то не сработало.

**Адрес: https://zTRPGz.github.io/pravovoy-konsultant/** — он собирается из
логина и имени репозитория, а не из названия проекта.

## Шпаргалка: что делать в повседневной работе

| Что нужно | Что сделать |
|----|----|
| **Обновить сайт после правки файлов** | `git add . && git commit -m "Правка" && git push` — дальше всё само, 1–2 минуты |
| Поправить мелочь без git | открыть файл на github.com → значок карандаша → **Commit changes** |
| Обновить базу законов, не дожидаясь ночи | Actions → «Обновление базы» → **Run workflow** |
| Посмотреть, что изменилось за ночь | вкладка **Actions** → последний прогон → вложение **update-logs** |
| Узнать версию базы у читателя | раздел **«Проверка актуальности»** в приложении |
| Проверить всё перед push | `npm run verify` — три проверки: `audit`, `verify-data`, `smoke-test` |

Настраивать больше нечего: репозиторий публичный, Pages включён, ночная
сборка и публикация работают. **Правки и обновления базы — это обычные
коммиты:** вы пушите, GitHub сам пересобирает сайт и выкладывает его, а
открытые вкладки читателей предлагают обновиться.

> **Что не попадает в открытый доступ.** Рабочие заметки ассистента
> (`.workbuddy-ai/`) в репозиторий не идут: каталог исключён в `.gitignore`
> целиком и **вычищен из истории** — иначе он всё равно оставался бы виден в
> старых коммитах. Проверить, что не осталось ни следа:
>
> ```bash
> git log --all --name-only --pretty=format: | sort -u | grep workbuddy   # пусто
> ```

## 1. Что где живёт

| Что | Где | Зачем |
|----|----|----|
| Сайт | `index.html`, `app.js`, `styles.css`, `data/*.js` | то, что отдаётся посетителю |
| **Каталог публикации** | **`dist/`** | **ровно то, что уходит на хостинг — собирается `npm run dist`** |
| Данные (собраны) | `data/` — 330 источников, 22 658 статей, полные тексты, граф ссылок, лента «Новое» | ~131 МБ |
| Сырые выгрузки | `vendor/` | **в git не входят** — каждый прогон качает заново |
| Инструменты | `tools/` | загрузка, сборка, аудит, проверки, лента |
| Ночная сборка | `.github/workflows/update.yml` | скачать → собрать → проверить → закоммитить |
| Публикация | `.github/workflows/pages.yml` | собрать `dist/` и выложить на GitHub Pages |
| Входная страница | `README.md` | что это за проект, как запустить, команды |
| Условия использования | `LICENSE` | репозиторий публичный — права объявлены словами |

`README.md` и `LICENSE` на хостинг **не уходят**: это документы репозитория,
а не сайта. Права для читателя сайта сказаны в самом приложении — в
дисклеймере внизу разделов.

**Размеры — главное, что нужно знать про хостинг.**

| Показатель | Значение |
|----|----|
| Каталог публикации `dist/` | **385 файлов, 131 МБ** |
| Самый большой файл | `data/full/nk2.js` — **9,6 МБ** |
| `data/` целиком | ~131 МБ |
| Из них полные тексты `data/full/` | 118 МБ (330 файлов) |

Лимит GitHub — 100 МБ на отдельный файл, лимит GitHub Pages — 1 ГБ на сайт:
и то и другое с запасом.

**Почему GitHub Pages.** Он открывается из России без VPN, даёт 100 ГБ
трафика в месяц, а репозиторий на GitHub всё равно нужен — там живёт ночная
сборка. Плата за это: репозиторий должен быть **публичным** (на бесплатном
плане Pages иначе не включается), а свои заголовки кеширования задать нельзя
— кеш там фиксированный, 10 минут. Механизму обновления из §2 это не мешает:
метка версии в адресе перезагрузки обходит кеш.

## 2. Как сайт обновляется сам

Требование было: «чтобы сайт у всех сам автоматически обновлялся». Работают
две независимые части — ночная пересборка на GitHub (§3) и опрос версии в
браузере.

### 2.1. Отпечаток сборки

`tools/build-data.js` вместе с данными пишет крошечный `data/version.json`:

```json
{"at":"2026-10-14T18:20:00.000Z","digest":"3134a093a9ef8925","articles":22658,"sources":330,"files":377,"code":"…"}
```

`digest` — это sha1 по содержимому всех `data/*.js` и `data/*.json`, у которых
предварительно обнулена метка времени `built_at`. Поэтому отпечаток меняется
**только вместе с самими данными**, а не каждую ночь: иначе все открытые вкладки
перезагружались бы впустую. Проверено: два прогона подряд дают одинаковый
`digest` при разном `at`.

Второе поле, `code`, — отпечаток **кода** (см. §2.4). Правка в `app.js`,
`styles.css` или `index.html` содержимое `data/` не меняет, поэтому по
`digest` её не увидеть, и без `code` такая правка не доезжала бы до читателя,
пока он сам не нажмёт Ctrl+F5.

### 2.2. Что делает браузер

`app.js` при старте один раз тихо читает `data/version.json` (с `cache:
"no-store"`), запоминает отпечаток в `localStorage` под ключом
`rflaws.buildDigest` и дальше перепроверяет его:

- раз в **45 минут**;
- при **возврате во вкладку** (`visibilitychange`), но не чаще раза в 5 минут.

Если отпечаток на хостинге разошёлся с загруженным — снизу появляется
уведомление **«Вышла новая редакция базы»** с числом статей и кнопками
«Обновить» и «Скрыть» (скрытие действует до конца сеанса). Кнопка «Обновить»
перезагружает страницу по адресу с меткой версии (`?v=<отпечаток>`), поэтому и
документ, и данные приходят из сети, а не из кеша. Текст уведомления честный:
если изменился только код, так и написано — «обновлён код приложения, тексты
законов не менялись».

Тяжёлые ленивые файлы (`data/ft/*`, `data/full/*`, `data/graph.js`) тоже
запрашиваются с `?v=<отпечаток>`, иначе после выкладки браузер отдал бы из
кеша старые тексты.

**Важная деталь.** Свежая загрузка страницы всегда отдаёт текущую сборку —
поэтому уведомление не показывается тем, кто просто открыл сайт: при старте
отпечаток молча запоминается. Оно адресовано тем, **кто читает приложение в
момент выкладки новой версии**: для них перезагрузка — единственный способ
получить новые тексты. Исключение — случай из §2.3, когда файлы данных пришли
из кеша браузера: тогда уведомление показывается и при первом опросе.

Текущую версию всегда видно в разделе **«Проверка актуальности»** — строка
«Версия базы в этой вкладке».

### 2.3. GitHub Pages и кеш браузера

Здесь есть ловушка, которой не было бы на хостинге с настраиваемыми
заголовками. GitHub Pages отдаёт **все** файлы с `Cache-Control: max-age=600`
и задавать свои заголовки не даёт. Само по себе это безобидно, но в одном
сценарии ломает главное — доставку обновлений:

1. читатель открыл сайт — файлы данных осели в кеше браузера на 10 минут;
2. вышла новая редакция базы;
3. уведомление появилось (`version.json` запрашивается мимо кеша);
4. человек нажимает «Обновить» — страница перезагружается, **а браузер снова
   отдаёт те же файлы данных из кеша**.

Вышло бы худшее из возможного: кнопка есть, обещание есть, а новых статей нет.
Поэтому сделаны две вещи.

**Метка версии в адресах данных.** В `index.html` файлы данных подключает
маленький загрузчик: если в адресе страницы есть `?v=<отпечаток>`, он
дописывает эту метку каждому файлу. Кнопка «Обновить» переходит на адрес с
меткой — значит, все данные приходят из сети, а не из кеша. На первом заходе и
на `file://` метки нет, и адреса остаются обычными.

**Сравнение меток сборки.** Сборщик пишет метку времени из одного значения в
два места: `at` в `data/version.json` и `built_at` в файлах данных. Приложение
сравнивает серверную метку с той, с которой загружены данные. Разошлись —
значит файлы пришли из кеша, и уведомление показывается **даже при первом
опросе**: иначе отпечатки совпали бы, и читатель остался бы со старым текстом
навсегда.

Проверяется это не рассуждением, а в настоящем браузере с настоящим кешем:
локальный стенд делает копию каталога публикации, отдаёт её с теми же 10
минутами кеша, «выпускает» новую сборку правкой файлов — и следит, что
уведомление появляется, кнопка ведёт на адрес с меткой, файлы данных
запрашиваются заново, а после перезагрузки на экране именно новая сборка.
Локальный сервер для этого умеет притворяться GitHub Pages:

```bash
node tools/build-dist.js
SERVE_CACHE=pages node tools/serve.js 8146 .workbuddy-ai/tmp-upd
node .workbuddy-ai/verify-update.js 8146
```

### 2.4. Что именно уходит на хостинг

В корне репозитория лежит не только сайт: там же `tools/` (исходники
сборщика), `.github/` (ночная сборка), `package.json` и эта инструкция.
Отдавать корень целиком не стоит — служебные файлы стали бы доступны по
прямым ссылкам. Поэтому публикуется собранный каталог `dist/`:

```bash
npm run dist      # собирает dist/ из index.html, app.js, styles.css, favicon.svg, sw.js, robots.txt и data/
```

Скрипт `tools/build-dist.js` кладёт туда же:

- **`_headers`** — правила кеширования. Они не дублируются, а **выводятся из
  `vercel.json`**: два списка рано или поздно разошлись бы, и кеш на одном
  хостинге отличался бы от кеша на другом;
- **`.nojekyll`** — без него GitHub Pages выбрасывает файлы, начинающиеся с
  подчёркивания, то есть сам `_headers`.

Последним шагом сборщик зовёт `applyCodeStamp(dist)`: подставляет отпечаток
кода в `dist/app.js` (`BUILD_CODE`) и в `dist/data/version.json` (`code`) —
одно и то же значение в двух местах, иначе плашка «обновитесь» висела бы
вечно. Значение константы и переводы строк нормализуются: без этого отпечаток
менялся бы от одной пересборки к другой.

`sw.js` (офлайн-работа) и `robots.txt` уходят на хостинг, `README.md` и
`LICENSE` — нет: это документы репозитория.

`dist/` в git не хранится — это производная от `data/`, её собирает хостинг.

Посмотреть, что именно уедет на хостинг, можно локально:

```bash
node tools/serve.js 8123 dist     # http://localhost:8123 — ровно содержимое dist/
```

Правила кеширования в `vercel.json` (переносятся в `dist/_headers`):

- `/`, `/index.html`, `/app.js`, `/styles.css` — `max-age=0, must-revalidate`:
  при каждом заходе браузер перепроверяет файл, поэтому новая версия сайта
  видна сразу после деплоя;
- `data/*.js` верхнего уровня (`index.js`, `registry.js`, `version.json`…) —
  тоже всегда перепроверяются;
- `data/full/*`, `data/ft/*` и `data/graph.js` (тяжёлые тексты и граф) —
  10 минут кеша с фоновым обновлением. После выкладки браузер подхватывает их
  по метке `?v=<отпечаток>`, поэтому залипнуть надолго они не могут.

На GitHub Pages свои заголовки задать нельзя — там кеш управляется правилами
самого GitHub. Механизм из §2.2 всё равно работает: метка версии в адресе
перезагрузки обходит кеш и там.

## 3. Ночная сборка и публикация: GitHub Actions

Файл `.github/workflows/update.yml` запускается **каждый день в 23:30 МСК** и
делает по шагам:

1. `fetch-sources.js` — кодексы и федеральные законы из открытого набора
   `ruslaw-public` (первоисточник — actual.pravo.gov.ru);
2. `fetch-extra.js` — Конституция, ФКЗ и метаданные прямо с портала;
3. `fetch-plenums.js` — постановления Пленума ВС РФ (sudact.ru);
4. `fetch-reviews.js` — обзоры судебной практики и постановления Президиума
   ВС РФ (sudact.ru);
5. `build-data.js` — пересборка `data/` (реестр, индекс, статусы, полнотекст,
   **граф перекрёстных ссылок**) и запись нового `data/version.json`;
6. `build-changelog.js` — сравнение с предыдущим снимком и лента изменений
   для вкладки «Новое»;
7. `audit.js` → `verify-data.js` → `smoke-test.js` — три проверки;
8. если хоть что-то изменилось и все проверки зелёные — коммит и `push`.
   Хостинг видит push и перевыкладывает сайт (`.github/workflows/pages.yml`),
   а открытые вкладки замечают новый отпечаток и предлагают обновиться.

**В `main` попадает только то, что прошло проверки.** Если хоть одна красная —
задача падает, коммита нет, на сайте остаётся прежняя база.

Сравнение «что изменилось» игнорирует сам `data/version.json`: его метка
времени меняется каждый прогон, а содержимое следует за остальными файлами.
Без этого правила коммит появлялся бы каждую ночь даже без изменений в законах.

**Включать ничего не нужно:** файл в репозитории — задача появляется в разделе
**Actions** сразу после первого пуша. Расписание начинает работать в течение
часа (GitHub может задержать первый запуск).

**Запустить вручную:** Actions → «Обновление базы» → **Run workflow**. Там же
можно отметить «пересобрать даже без изменений».

**Логи любого прогона** (в том числе упавшего) — во вложении `update-logs`.

> **Граф ссылок** (`data/graph.js`) считается при сборке по текстам актов и
> сверяется с ними в `verify-data.js`. Если файл разошёлся с текстами, проверка
> скажет об этом — значит, данные обновили, а граф не пересобрали.

## 4. Обновить сайт руками

Отдельного файлового менеджера не нужно — обновление это обычный коммит.

**Свой текст или правка интерфейса:**

```bash
git add .
git commit -m "Правка текста справки"
git push
```

Хостинг перевыложит сайт за минуту-две; открытые вкладки покажут уведомление
из §2.

**Только данные о статьях:**

```bash
npm run build      # скачать свежие тексты с портала и пересобрать data/
npm run verify     # три проверки: audit + verify-data + smoke-test
git add data tools/state/snapshot.json
git commit -m "Обновление базы"
git push
```

Руками править `data/*.js` не нужно: это результат сборки. Собирать `dist/`
локально тоже не нужно — это делает задача «Публикация» при каждом push.

## 5. Вкладка «Новое»

Заполняется автоматически ночной сборкой. Одна запись — один документ на одну
дату проверки:

- сменилась редакция (с указанием прежней и новой даты);
- добавились, изменились или исчезли статьи — со ссылками на каждую;
- нормы утратили силу или снова действуют — со ссылками на статьи;
- документ добавлен в базу или убран из неё.

У непросмотренных записей в боковом меню горит счётчик и точка; кнопка
**«Отметить прочитанным»** снимает их. Просмотр не требует сети — лента уже
лежит в собранной базе (`data/changelog.js`).

Если лента пуста, раздел так и говорит: «Лента пока пуста» — с инструкцией,
чем её запустить.

## 6. Локальные команды

```bash
npm run verify     # три проверки: audit + verify-data + smoke-test
npm run build      # полный цикл: скачать → собрать → лента
npm run build:data # только пересборка данных и ленты (без скачивания)
npm run changelog  # пересчитать ленту из текущих данных
npm run dist       # собрать каталог публикации dist/
npm run serve      # http://localhost:8080 — просмотр как на хостинге
node tools/serve.js 8123 dist   # просмотр ровно того, что уедет на хостинг
node tools/smoke-test.js        # прогон интерфейса (нужен jsdom: npm ci)
```

Первый `npm run build` скачает ~92 МБ сырых выгрузок в `vendor/` — в git они не
идут, так что при клонировании репозитория их нужно получить этой командой.

Проверить отпечаток сборки вручную:

```bash
cat data/version.json
```

## 7. Правило хранения ленты

Лента не растёт бесконечно: `tools/build-changelog.js` оставляет записи за
последние **180 дней**, но не больше **400 штук**. Сравниваемый снимок лежит в
`tools/state/snapshot.json` — он нужен сборке, но в браузер не попадает.

Если ночная сборка не смогла ничего изменить (портал недоступен, проверка
красная), коммита не будет — и лента останется честной, без придуманных записей.

> **Осторожно с лентой.** `build-changelog.js` **сливает** новый дифф с уже
> лежащим `data/changelog.js`, поэтому ошибочная запись («убран из базы»)
> останется там навсегда. Пересобрать с чистого листа: вернуть
> `tools/state/snapshot.json` из HEAD, очистить `data/changelog.js` и запустить
> сборку заново.
