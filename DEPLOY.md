# Правовой консультант — публикация и автообновление

Приложение — статический сайт без сервера и без сборки: HTML, CSS, один
`app.js` и данные в `data/`. Работает и с `file://`, и с любого хостинга.
Ниже — как выложить его так, чтобы он **обновлялся сам у всех посетителей**,
и как просто загружать новые файлы, когда что-то изменилось.

---

## Шпаргалка: сайт уже опубликован

Адрес: **https://zTRPGz.github.io/pravovoy-konsultant/**
Он собирается из логина и имени репозитория — не из названия проекта.

| Что нужно | Что сделать |
|----|----|
| **Обновить сайт после правки файлов** | `git add . && git commit -m "Правка" && git push` — дальше всё само, 1–2 минуты |
| Поправить мелочь без git | открыть файл на github.com → значок карандаша → **Commit changes** |
| Обновить базу законов, не дожидаясь ночи | Actions → «Обновление базы» → **Run workflow** |
| Посмотреть, что изменилось за ночь | вкладка **Actions** → последний прогон → вложение **update-logs** |
| Узнать версию базы у читателя | раздел **«Проверка актуальности»** в приложении |

Настраивать больше нечего: репозиторий публичный, Pages включён, ночная
сборка и публикация уже работают. **Правки и обновления базы — это обычные
коммиты:** вы пушите, GitHub сам пересобирает сайт и выкладывает его, а
открытые вкладки читателей предлагают обновиться. Подробности — в разделах
ниже, короткая версия — в §5 «Просто загрузить новые файлы».

## Короткий путь: от нуля до живого сайта

Если вы ещё ничего никуда не загружали — вот вся последовательность целиком.
Подробности по каждому шагу — в разделах ниже.

> **Сначала о выборе хостинга — он тут не свободный.** Сайт рассчитан на
> читателя в России, а часть зарубежных площадок из России **без VPN не
> открывается вообще**: это `*.vercel.app` и `pages.dev` (Cloudflare Pages).
> Замер и подробности — в §3.1. Поэтому публикуемся на **GitHub Pages**:
> он из России открывается, бесплатен и даёт 100 ГБ трафика в месяц.

**Шаг 1. Настроить git (один раз на компьютере).**
Без имени и почты git откажется делать коммит:

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "ваша@почта"
```

> **Если PowerShell пишет «Имя "git" не распознано».** Значит, отдельного Git на
> компьютере нет — есть только переносимый, который поставляется вместе с
> приложением. Он лежит в
> `C:\Program Files\WorkBuddyAI\resources\vendor\PortableGit\`. Добавьте его в
> `Path` текущего окна PowerShell — и команды заработают:
>
> ```powershell
> $env:Path += ";C:\Program Files\WorkBuddyAI\resources\vendor\PortableGit\cmd"
> cd C:\Users\<вы>\Downloads\rf-laws     # папка проекта — иначе git скажет «not a git repository»
> ```
>
> Настройка действует до закрытия окна: откроете новое — повторите строку.
> Чтобы `git` работал всегда и во всех программах, поставьте обычный
> [Git for Windows](https://git-scm.com/download/win) — установка со всеми
> настройками по умолчанию.

**Шаг 2. Создать репозиторий на GitHub.**
[github.com](https://github.com) → **New repository** → имя, например
`pravovoy-konsultant` → **Public** → не добавлять ни README, ни `.gitignore`
(иначе первый push конфликтует) → **Create repository**.

> **Почему именно Public.** GitHub Pages на бесплатном плане работает только
> из публичных репозиториев — из приватного он включается лишь на платном
> GitHub Pro. Сайт всё равно публичный, а исходники справочника скрывать
> нечего. Единственное, что не должно попасть в открытый доступ, — рабочие
> заметки ассистента: они исключены из репозитория и вычищены из истории
> (`.gitignore`, §3.3).

**Шаг 3. Отправить проект в репозиторий.** Из папки проекта:

```bash
git init                       # если папка ещё не репозиторий; повторный запуск безвреден
git add .
git commit -m "Правовой консультант: первая публикация"
git branch -M main
git remote add origin https://github.com/<ваш-логин>/pravovoy-konsultant.git
git push -u origin main
```

Уйдёт **300 файлов, ~101 МБ** — на небыстром канале это несколько минут.

**Шаг 4. Разрешить ночной сборке писать в репозиторий.**
Репозиторий → **Settings → Actions → General → Workflow permissions** →
**Read and write permissions** → **Save**.

**Шаг 5. Включить GitHub Pages.**
Репозиторий → **Settings → Pages** → **Build and deployment** →
**Source: GitHub Actions**. Больше настраивать нечего: файл
`.github/workflows/pages.yml` уже лежит в репозитории — он собирает каталог
`dist/` и выкладывает его.

Затем **Actions → «Публикация» → Run workflow**, чтобы выложить сайт не
дожидаясь следующего push. Первая выкладка занимает 1–3 минуты.

**Шаг 6. Проверить.**
Открыть `https://<ваш-логин>.github.io/pravovoy-konsultant/` — сайт должен
работать. Затем
`https://<ваш-логин>.github.io/pravovoy-konsultant/data/version.json` —
должен вернуться JSON с отпечатком сборки.

> **Адрес получается из логина и имени репозитория** — не из названия
> проекта, как на других площадках. Переименование репозитория меняет адрес.
> Свой домен тоже можно подключить: **Settings → Pages → Custom domain**.

Готово. Дальше сайт обновляется сам: ночью GitHub Actions проверяет законы и,
если что-то изменилось, коммитит; хостинг перевыкладывает; открытые вкладки
предлагают обновиться.

## 2. Автообновление у посетителей (как это устроено)

Требование было: «чтобы сайт у всех сам автоматически обновлялся». Работают
две независимые части — ночная пересборка на GitHub и опрос версии в браузере.

### 2.1. Отпечаток сборки

`tools/build-data.js` вместе с данными пишет крошечный `data/version.json`:

```json
{"at":"2026-10-12T01:45:35.064Z","digest":"e7dfe6191e8bc64a","articles":19307,"sources":227,"files":271}
```

`digest` — это sha1 по содержимому всех `data/*.js` и `data/*.json`, у которых
предварительно обнулена метка времени `built_at`. Поэтому отпечаток меняется
**только вместе с самими данными**, а не каждую ночь: иначе все открытые вкладки
перезагружались бы впустую. Проверено: два прогона подряд дают одинаковый
`digest` при разном `at`.

### 2.2. Что делает браузер

`app.js` при старте один раз тихо читает `data/version.json` (с `cache:
"no-store"`), запоминает отпечаток в `localStorage` под ключом
`rflaws.buildDigest` и дальше перепроверяет его:

- раз в **45 минут**;
- при **возврате во вкладку** (`visibilitychange`), но не чаще раза в 5 минут.

Если отпечаток на хостинге разошёлся с загруженным — снизу появляется
уведомление **«Вышла новая редакция базы»** с числом статей и кнопками
«Обновить» и «Скрыть» (скрытие действует до конца сеанса). Кнопка «Обновить»
перезагружает страницу по адресу с меткой версии (`?v=<отпечаток>`), поэтому и
документ, и данные приходят из сети, а не из кеша.

Тяжёлые ленивые файлы (`data/ft/*`, `data/full/*`) тоже запрашиваются с
`?v=<отпечаток>`, иначе после выкладки браузер отдал бы из кеша старые тексты.

**Важная деталь.** Свежая загрузка страницы всегда отдаёт текущую сборку —
поэтому уведомление не показывается тем, кто просто открыл сайт: при старте
отпечаток молча запоминается. Оно адресовано тем, **кто читает приложение в
момент выкладки новой версии**: для них перезагрузка — единственный способ
получить новые тексты. Исключение — случай из §2.3, когда файлы данных пришли
из кеша браузера: тогда уведомление показывается и при первом опросе.

Текущую версию всегда видно в разделе **«Проверка актуальности»** — строка
«Версия базы в этой вкладке».

### 2.3. GitHub Pages и кеш браузера

Здесь есть ловушка, которой не было бы на хостинге с настраиваемыми
заголовками. GitHub Pages отдаёт **все** файлы с `Cache-Control: max-age=600`
и задавать свои заголовки не даёт. Само по себе это безобидно, но в одном
сценарии ломает главное — доставку обновлений:

1. читатель открыл сайт — файлы данных осели в кеше браузера на 10 минут;
2. вышла новая редакция базы;
3. уведомление появилось (`version.json` запрашивается мимо кеша);
4. человек нажимает «Обновить» — страница перезагружается, **а браузер снова
   отдаёт те же файлы данных из кеша**.

Вышло бы худшее из возможного: кнопка есть, обещание есть, а новых статей нет.
Поэтому сделаны две вещи.

**Метка версии в адресах данных.** В `index.html` файлы данных подключает
маленький загрузчик: если в адресе страницы есть `?v=<отпечаток>`, он
дописывает эту метку каждому файлу. Кнопка «Обновить» переходит на адрес с
меткой — значит, все данные приходят из сети, а не из кеша. На первом заходе и
на `file://` метки нет, и адреса остаются обычными.

**Сравнение меток сборки.** Сборщик пишет метку времени из одного значения в
два места: `at` в `data/version.json` и `built_at` в файлах данных. Приложение
сравнивает серверную метку с той, с которой загружены данные. Разошлись —
значит файлы пришли из кеша, и уведомление показывается **даже при первом
опросе**: иначе отпечатки совпали бы, и читатель остался бы со старым текстом
навсегда.

Проверяется это не рассуждением, а в настоящем браузере с настоящим кешем:
`.workbuddy-ai/verify-update.js` делает копию каталога публикации, отдаёт её с
теми же 10 минутами кеша, «выпускает» новую сборку правкой файлов — и следит,
что уведомление появляется, кнопка ведёт на адрес с меткой, файлы данных
запрашиваются заново, а после перезагрузки на экране именно новая сборка.
Локальный сервер для этого умеет притворяться GitHub Pages:

```bash
node tools/build-dist.js
SERVE_CACHE=pages node tools/serve.js 8146 .workbuddy-ai/tmp-upd
node .workbuddy-ai/verify-update.js 8146
```

## 3. Куда публиковать

### 3.0. Что именно уходит на хостинг

В корне репозитория лежит не только сайт: там же `tools/` (исходники сборщика),
`.github/` (ночная сборка), `package.json` и эта инструкция. Отдавать корень
целиком не стоит — служебные файлы стали бы доступны по прямым ссылкам. Поэтому
публикуется собранный каталог `dist/`:

```bash
npm run dist      # собирает dist/ из index.html, app.js, styles.css, favicon.svg, sw.js, robots.txt и data/
```

Скрипт `tools/build-dist.js` кладёт туда же:

- **`_headers`** — правила кеширования. Они не дублируются, а **выводятся из
  `vercel.json`**: два списка рано или поздно разошлись бы, и кеш на Vercel
  отличался бы от кеша на Cloudflare;
- **`.nojekyll`** — без него GitHub Pages выбрасывает файлы, начинающиеся с
  подчёркивания, то есть сам `_headers`.

Последним шагом сборщик зовёт `applyCodeStamp(dist)`: подставляет отпечаток
кода в `dist/app.js` (`BUILD_CODE`) и в `dist/data/version.json` (`code`) —
одно и то же значение в двух местах, иначе плашка «обновитесь» висела бы
вечно.

`sw.js` (офлайн-работа) и `robots.txt` уходят на хостинг, `README.md` и
`LICENSE` — нет: это документы репозитория.

`dist/` в git не хранится — это производная от `data/`, её собирает хостинг.

Посмотреть, что именно уедет на хостинг, можно локально:

```bash
node tools/serve.js 8123 dist     # http://localhost:8123 — ровно содержимое dist/
```

Сборщик сам сообщает объём и предупреждает, если превышены пределы бесплатного
Cloudflare Pages (25 МБ на файл, 20 000 файлов).

### 3.1. Сравнение

**Первое, что здесь важно, — не лимиты, а доступность из России.** Сайт
рассчитан на читателя в России, и часть площадок оттуда **без VPN не
открывается вообще**. Замер `curl` с обычного российского подключения:

| Адрес | Ответ |
|----|----|
| `*.vercel.app` (64.29.17.x, 216.198.79.x) | **таймаут — недоступен** |
| `pages.dev` (104.18.20.x) и `*.pages.dev` | **таймаут / DNS-таймаут** |
| `cloudflare.com` (104.16.x) | 301 ✅ |
| `github.io`, `<логин>.github.io` (185.199.108–111.153) | ✅ отвечает |
| `netlify.app` (63.176.8.218), `app.netlify.com` | ✅ отвечает |
| `storage.yandexcloud.net`, `timeweb.cloud`, `beget.com` | ✅ отвечает |

Блокировка идёт по конкретным адресам и диапазонам, а не «по хостингу
целиком»: `cloudflare.com` открывается, а `pages.dev` — нет. Отсюда вывод:
**Vercel и Cloudflare Pages для этого проекта отпадают** — сайт на них
заведётся и будет открываться через VPN, но читатель из России увидит таймаут.

| Хостинг | Из РФ без VPN | Лимит | Наш `dist/` (100,3 МБ, 278 файлов, макс. 9,6 МБ) |
|----|----|----|----|
| **GitHub Pages**, бесплатно | ✅ | 1 ГБ на сайт, 100 ГБ трафика в месяц, 10 сборок в час; репозиторий должен быть **публичным** (на Free) | ✅ подходит |
| **Netlify**, бесплатно | ✅ | 300 кредитов в месяц, трафик 20 кредитов за гигабайт — то есть ≈ **15 ГБ** | ✅ подходит |
| **Cloudflare Pages**, бесплатно | ❌ **только через VPN** | 25 МБ на файл, 20 000 файлов, трафик без лимита, 500 сборок в месяц | ✅ по размеру, но читатель не откроет |
| **Vercel Hobby**, бесплатно | ❌ **только через VPN** | **100 МБ на загрузку деплоя** | ❌ и по размеру не укладывается |
| **Российский хостинг** (Timeweb, Beget, Яндекс Облако) | ✅ | зависит от тарифа, оплата рублями | ✅ подходит |

### 3.2. Рекомендация

**Берите GitHub Pages** (§3.5). Три причины:

1. **открывается из России** — то, ради чего всё и затевается;
2. **100 ГБ трафика в месяц** — у бесплатного Netlify лимит в шесть раз
   меньше, а справочник по законам читают много и подолгу;
3. **репозиторий на GitHub всё равно нужен** — там живёт ночная сборка, так что
   отдельный сервис подключать не придётся.

Цена: репозиторий должен быть публичным, и свои заголовки кеширования задать
нельзя — кеш там фиксированный (10 минут), поэтому новая версия доходит до
читателя не мгновенно, а в пределах десяти минут. Механизм из раздела 2 от
этого не страдает: метка версии в адресе перезагрузки обходит кеш.

**Netlify** (§3.7) — если публичный репозиторий не подходит: из России
читается, репозиторий остаётся приватным, настройка проще. Минус — трафика в
шесть раз меньше.

**Российский хостинг** — если читателей планируется много: доступен
гарантированно, оплата рублями. Дороже по времени: файлы загружаются вручную
(FTP или объектное хранилище), автоматической выкладки по push не будет.

**Cloudflare Pages** (§3.4) и **Vercel** (§3.6) описаны ниже — они удобнее и
щедрее по лимитам, но из России без VPN недоступны, поэтому для этого проекта
не годятся.

> **Можно ли всё-таки остаться на бесплатном Vercel?** Да, но ценой лишней
> зависимости: 90 из 100 МБ — это `data/full/` (полные тексты актов), и их
> можно вынести за пределы деплоя, отдавая с внешнего адреса. Тогда деплой
> сжимается до ~10 МБ и проходит где угодно. Плата — доступность справочника
> начинает зависеть от чужого сервиса, который вы не контролируете. Ради
> экономии 20 $ в месяц это обычно не стоит того.

### 3.3. Первый push на GitHub (нужен для любого варианта)

```bash
git init
git add .
git commit -m "Правовой консультант: первая публикация"
git branch -M main
git remote add origin https://github.com/<ваш-логин>/<репозиторий>.git
git push -u origin main
```

`.gitignore` исключает `vendor/`, `node_modules/`, `dist/` и рабочие файлы
ассистента целиком — `.workbuddy-ai/`. Исключение из `.gitignore` действует
только на будущие коммиты, поэтому заметки вычищены ещё и из истории:

```bash
git rm -r --cached .workbuddy-ai
git commit -m "Рабочие заметки ассистента в репозиторий не входят"
git filter-branch --force --index-filter \
  'git rm -r --cached --ignore-unmatch .workbuddy-ai' --prune-empty -- --all
git push --force origin main
```

Проверить, что не осталось ни следа:

```bash
git log --all --name-only --pretty=format: | sort -u | grep workbuddy   # пусто
```

Репозиторий должен быть **публичным** — этого требует GitHub Pages на
бесплатном плане. Если публичность непринципиальна, но нежелательна, берите
Netlify (§3.7): там репозиторий можно оставить приватным.

### 3.4. Cloudflare Pages (удобно, но из России недоступно без VPN)

> **Сначала прочтите это.** Cloudflare Pages отдаёт сайты с адресов
> `pages.dev`, а этот домен из России не открывается (замер — §3.1). Проект
> заведётся, деплой пройдёт, но читатель увидит таймаут. Раздел сохранён для
> полноты: он пригодится, если сайт рассчитан на аудиторию вне России или
> если вы готовы платить за свой домен и проверять, открывается ли он.

1. [dash.cloudflare.com](https://dash.cloudflare.com) → **Workers & Pages →
   Create → Pages → Connect to Git**, выберите репозиторий из §3.3.
2. **Project name** — впишите название сайта, например `pravovoy-konsultant`.
   **Именно из этого поля получится адрес**, и его вы выбираете сами; почта
   аккаунта в адрес не попадает (подробнее ниже).
3. Настройки сборки:
   - **Build command:** `node tools/build-dist.js`
   - **Build output directory:** `dist`
   - **Root directory:** оставьте пустым (корень репозитория)
4. **Save and Deploy.** Через минуту-две сайт будет доступен на
   `https://pravovoy-konsultant.pages.dev`.
5. Дальше каждый `git push` в `main` — в том числе коммит ночной сборки —
   перевыкладывает сайт автоматически. Ничего настраивать больше не нужно.

Если выбранное имя уже занято другим проектом Cloudflare, к нему добавятся
несколько случайных символов (`pravovoy-konsultant-a1b2.pages.dev`) — просто
возьмите другое слово. Уже созданный проект можно переименовать: **Settings →
Project name**; адрес изменится вместе с именем.

Свой домен: **Custom domains → Set up a domain**. Подключается бесплатно,
сертификат выпускается сам.

**Про адрес сайта.** `https://<название-проекта>.pages.dev` — это название
**проекта**, а не аккаунта, и почта в него не попадает. По умолчанию Cloudflare
подставляет имя git-репозитория, но его можно заменить на любое: при создании —
в поле **Project name**, позже — в **Settings → Project name**. Например, имя
`pravovoy-konsultant` даёт адрес `pravovoy-konsultant.pages.dev`.

Если подсказка в поле имени выглядит как адрес вашей почты (`ivan-gmail-com`) —
это лишь значение по умолчанию для аккаунтов, заведённых через почту. Сотрите
его и впишите любое слово. А если не хочется и `pages.dev`, подключите свой
домен — тогда адрес будет полностью вашим.

**Проверка после первого деплоя.** Откройте
`https://<проект>.pages.dev/data/version.json` — должен вернуться JSON с
отпечатком (`{"at":…,"digest":…}`). Если вместо него пришёл HTML, значит
каталог сборки указан неверно и отдаётся что-то другое.

### 3.5. GitHub Pages (бесплатно, работает из России, рекомендуется)

**Что нужно от репозитория.** Он должен быть **публичным**: на бесплатном
плане GitHub Pages включается только для публичных репозиториев (для приватных
нужен GitHub Pro). Сайт всё равно публичный, а исходники справочника скрывать
нечего — из репозитория убраны только рабочие заметки ассистента (§3.3).

**Что нужно сделать в настройках:**

1. **Settings → Pages → Build and deployment → Source: GitHub Actions.**
2. **Settings → Actions → General → Workflow permissions → Read and write
   permissions → Save** — иначе ночная сборка не сможет коммитить новые тексты.
3. **Actions → «Публикация» → Run workflow** — чтобы выложить сайт сразу, не
   дожидаясь следующего push.

**Файл задачи уже в репозитории** — `.github/workflows/pages.yml`, создавать
ничего не нужно. Он делает то же, что и локальный `npm run dist`: собирает
каталог публикации и выкладывает его.

```yaml
- run: node tools/build-dist.js          # собирает dist/
- uses: actions/upload-pages-artifact@v3
  with: { path: dist }                  # уходит только dist/, не корень
- uses: actions/deploy-pages@v4          # выкладка
```

Дальше сайт выкладывается сам на каждый `push` в `main` — включая коммиты
ночной сборки.

**Адрес:** `https://<логин>.github.io/<репозиторий>/` — он собирается из логина
и имени репозитория. Свой домен: **Settings → Pages → Custom domain**.

**Про подкаталог.** Проектный сайт живёт не в корне домена, а по пути
`/<репозиторий>/`. Приложение использует только относительные пути, поэтому
работает там без правок — это проверено в настоящем браузере: страница
открывается, отпечаток сборки читается, ленивый полный текст статьи
(`data/full/<источник>.js`) запрашивается из подкаталога, ни одного запроса
мимо и ни одной ошибки в консоли. Проверить у себя можно так:

```bash
mkdir -p .workbuddy-ai/tmp-gh/pravovoy-konsultant
cp -r dist/. .workbuddy-ai/tmp-gh/pravovoy-konsultant/
node tools/serve.js 8145 .workbuddy-ai/tmp-gh     # http://localhost:8145/pravovoy-konsultant/
```

**Чего не будет.** Своих заголовков кеширования — GitHub их задавать не даёт,
кеш фиксированный (10 минут). Механизму из раздела 2 это не мешает: файлы
данных получают метку версии, а расхождение меток сборки ловится отдельно
(§2.3). Единственная видимая разница: файл, который вы только что переписали,
читатель получит не мгновенно, а в пределах десяти минут.

### 3.6. Vercel (недоступен из России, плюс нужен платный план)

1. [vercel.com](https://vercel.com): **Add New → Project → Import Git
   Repository**, выберите репозиторий из §3.3.
2. **Build command:** `node tools/build-dist.js`, **Output directory:** `dist`.
3. **Deploy.** Адрес вида `https://<проект>.vercel.app`.

> **Почему не подходит.** Две причины, каждой достаточно. Первая: сайты на
> `*.vercel.app` из России **без VPN не открываются** (замер — §3.1), то есть
> читатель увидит таймаут. Вторая: Vercel Hobby принимает не более **100 МБ**
> исходных файлов на деплой, а у нас 100,3 МБ одних данных — деплой упадёт с
> ошибкой о размере. Варианты: Pro (лимит 1 ГБ) плюс свой домен, но
> блокировка идёт по адресам Vercel, так что и он не поможет.

### 3.7. Netlify (бесплатно, из России читается, репозиторий можно оставить приватным)

Запасной вариант, если публичный репозиторий не подходит. Главный минус —
бесплатный лимит трафика: **300 кредитов в месяц**, а трафик стоит 20 кредитов
за гигабайт, то есть около **15 ГБ** — это примерно 2 500 заходов (первый экран
весит 5,6 МБ). У GitHub Pages лимит в шесть раз больше.

1. [app.netlify.com](https://app.netlify.com) → **Add new site → Import an
   existing project → GitHub**, выберите репозиторий из §3.3.
2. **Build command:** `node tools/build-dist.js`,
   **Publish directory:** `dist`.
3. **Deploy site.** Адрес вида `https://<имя>.netlify.app`, имя меняется в
   **Site configuration → Site details → Change site name**.

Свой файл заголовков Netlify понимает так же, как Cloudflare: `_headers` из
`dist/` подхватывается автоматически, правила кеширования из раздела 2
работают без правок.

### Что уже настроено для кеша

Правила заданы в `vercel.json` и переносятся в `dist/_headers` при сборке:

- `/`, `/index.html`, `/app.js`, `/styles.css` — `max-age=0, must-revalidate`:
  при каждом заходе браузер перепроверяет файл, поэтому новая версия сайта
  видна сразу после деплоя;
- `data/*.js` верхнего уровня (`index.js`, `registry.js`, `version.json`…) —
  тоже всегда перепроверяются;
- `data/full/*` и `data/ft/*` (тяжёлые полные тексты) — 10 минут кеша с
  фоновым обновлением. После выкладки браузер подхватывает их по метке
  `?v=<отпечаток>`, поэтому залипнуть надолго они не могут.

На GitHub Pages свои заголовки задать нельзя — там кеш управляется правилами
самого GitHub. Механизм из раздела 2 всё равно работает: метка версии в адресе
перезагрузки обходит кеш и там.

## 4. Автообновление базы: GitHub Actions

Файл `.github/workflows/update.yml` запускается **каждый день в 23:30 МСК** и
делает по шагам:

1. `fetch-sources.js` — кодексы и федеральные законы из открытого набора
   `ruslaw-public` (первоисточник — actual.pravo.gov.ru);
2. `fetch-extra.js` — Конституция, ФКЗ и метаданные прямо с портала;
3. `fetch-plenums.js` — постановления Пленума ВС РФ (sudact.ru);
4. `build-data.js` — пересборка `data/` (реестр, индекс, статусы, полнотекст)
   **и запись нового `data/version.json`**;
5. `build-changelog.js` — сравнение с предыдущим снимком и лента изменений
   для вкладки «Новое»;
6. `audit.js` → `verify-data.js` → `smoke-test.js` — три проверки;
7. если хоть что-то изменилось и все проверки зелёные — коммит и `push`.
   Хостинг видит push и перевыкладывает сайт, а открытые вкладки замечают
   новый отпечаток и предлагают обновиться.

**В `main` попадает только то, что прошло проверки.** Если хоть одна красная —
задача падает, коммита нет, на сайте остаётся прежняя база.

Сравнение «что изменилось» игнорирует сам `data/version.json`: его метка
времени меняется каждый прогон, а содержимое следует за остальными файлами.
Без этого правила коммит появлялся бы каждую ночь даже без изменений в законах.

### Включить

Ничего включать не нужно: файл в репозитории — задача появится в разделе
**Actions** сразу после первого пуша. Расписание начнёт работать в течение
часа (GitHub может задержать первый запуск).

**Запустить вручную:** Actions → «Обновление базы» → **Run workflow**.
Там же можно отметить «пересобрать даже без изменений».

**Логи любого прогона** (в том числе упавшего) — во вложении `update-logs`.

## 5. «Просто загрузить новые файлы»

Отдельного файлового менеджера не нужно — обновление это обычный коммит.

**Свой текст или правка интерфейса:**

```bash
git add .
git commit -m "Правка текста справки"
git push
```

Хостинг перевыложит сайт за минуту-две; открытые вкладки покажут уведомление
из раздела 2.

**Только данные о статьях:**

```bash
npm run build      # скачать свежие тексты с портала и пересобрать data/
npm run verify     # три проверки: audit + verify-data + smoke-test
git add data tools/state/snapshot.json
git commit -m "Обновление базы"
git push
```

Руками править `data/*.js` не нужно: это результат сборки. Собирать `dist/`
локально тоже не нужно — это делает задача «Публикация» при каждом push. Если
очень хочется залить без git, можно собрать `npm run dist` и перетащить каталог
`dist/` в [app.netlify.com/drop](https://app.netlify.com/drop) — сайт появится
сразу, но автоматической ночной сборки там не будет: её выполняет только
GitHub Actions.

## 6. Вкладка «Новое»

Заполняется автоматически ночной сборкой. Одна запись — один документ на одну
дату проверки:

- сменилась редакция (с указанием прежней и новой даты);
- добавились, изменились или исчезли статьи — со ссылками на каждую;
- нормы утратили силу или снова действуют — со ссылками на статьи;
- документ добавлен в базу или убран из неё.

У непросмотренных записей в боковом меню горит счётчик и точка; кнопка
**«Отметить прочитанным»** снимает их. Просмотр не требует сети — лента уже
лежит в собранной базе (`data/changelog.js`).

Если лента пуста, раздел так и говорит: «Лента пока пуста» — с инструкцией,
чем её запустить.

## 7. Локальные команды

```bash
npm run verify     # три проверки: audit + verify-data + smoke-test
npm run build      # полный цикл: скачать → собрать → лента
npm run build:data # только пересборка данных и ленты (без скачивания)
npm run changelog  # пересчитать ленту из текущих данных
npm run dist       # собрать каталог публикации dist/
npm run serve      # http://localhost:8080 — просмотр как на хостинге
node tools/serve.js 8123 dist   # просмотр ровно того, что уедет на хостинг
node tools/smoke-test.js        # прогон интерфейса (нужен jsdom: npm ci)
```

Первый `npm run build` скачает ~92 МБ сырых выгрузок в `vendor/` — в git они не
идут, так что при клонировании репозитория их нужно получить этой командой.

Проверить отпечаток сборки вручную:

```bash
cat data/version.json
```

## 8. Правило хранения ленты

Лента не растёт бесконечно: `tools/build-changelog.js` оставляет записи за
последние **180 дней**, но не больше **400 штук**. Сравниваемый снимок лежит в
`tools/state/snapshot.json` — он нужен сборке, но в браузер не попадает.

Если ночная сборка не смогла ничего изменить (портал недоступен, проверка
красная), коммита не будет — и лента останется честной, без придуманных записей.
